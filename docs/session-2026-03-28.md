## 1. Infrastructure & Build Fixes

### 1.1 Root `tsconfig.json` Propagated to Docker Build Contexts

**Problem:** Four Docker images — `admin-app`, `user-app`, `landing`, and `mock-polymarket` — were failing at compile time with:

```
error TS5083: Cannot read file '/app/tsconfig.json'.
```

The root `tsconfig.json` was not being copied into each image's build context before `tsc` ran, so the `extends` chain in each app's own `tsconfig.json` could not resolve its base configuration.

**Fix:** Added a `COPY tsconfig.json .` instruction to the Dockerfile for each of the four services, ensuring the root config is present in the image layer before any TypeScript compilation step runs.

**Files affected:**
- `apps/admin-app/Dockerfile`
- `apps/user-app/Dockerfile`
- `apps/landing/Dockerfile`
- `services/mock-polymarket/Dockerfile`

---

### 1.2 `strictPropertyInitialization: false` Added to Root `tsconfig.json`

**Problem:** NestJS uses a class-based DTO and entity pattern where class properties are initialised by a decorator (e.g. `@IsString()`) or by the ORM, not by a TypeScript constructor. With `strict: true` in the root config, the compiler was emitting errors of the form:

```
error TS2564: Property 'X' has no initializer and is not definitely assigned in the constructor.
```

across all backend services that use NestJS DTOs.

**Fix:** Added `"strictPropertyInitialization": false` to `compilerOptions` in the root `tsconfig.json`. All other strict checks remain enabled — this is a targeted relaxation for the NestJS class-based pattern only.

**Current root `tsconfig.json`:**

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "CommonJS",
    "moduleResolution": "node",
    "lib": ["ES2022"],
    "strict": true,
    "strictPropertyInitialization": false,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "composite": true,
    "incremental": true,
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  },
  "exclude": ["node_modules"]
}
```

### 1.3 `lib` Updated in App `tsconfig.json` Files

**Problem:** `apps/admin-app` and `apps/user-app` are Vite + React applications that rely on DOM APIs (e.g. `document`, `window`, `ResizeObserver`). The root `tsconfig.json` only includes `"lib": ["ES2022"]`, which has no DOM type definitions. This produced `Cannot find name 'document'` and similar errors during the Vite type-check pass.

**Fix:** Added `"lib": ["ES2022", "DOM", "DOM.Iterable"]` to the `compilerOptions` in:
- `apps/admin-app/tsconfig.json`
- `apps/user-app/tsconfig.json`

These values extend (not replace) the root lib setting for just the browser-targeted packages.

### 1.4 Test Files Excluded from Production Builds

**Problem:** Vitest imports (`import { describe, it, expect } from 'vitest'`) were leaking into production type-check passes for `admin-app` and `user-app`, causing `Cannot find module 'vitest'` errors. The test files live under `src/__tests__/` and should only be compiled when Vitest runs, not when Vite builds for production.

**Fix:** Added `"exclude": ["src/__tests__"]` to both:
- `apps/admin-app/tsconfig.json`
- `apps/user-app/tsconfig.json`

### 1.5 Removed `@napi-rs/cli` and `wasm-pack` from Root `package.json`

**Problem:** `@napi-rs/cli` and `wasm-pack` are native build tools for the Rust/WASM compilation pipeline. They were incorrectly listed as root-level `devDependencies`. This caused two issues:

1. pnpm attempted to install native binaries for all CI environments, not just the Rust build step.
2. The presence of these packages at the root caused workspace-wide installation failures in Alpine-based Docker images that lack the necessary system libraries.

**Fix:** Removed both packages from `package.json` at the root. They belong exclusively in `packages/polyforge-crypto-native/package.json`, which is the workspace package responsible for building the WASM module.

### 1.6 `pnpm-lock.yaml` Fully Regenerated

**Problem:** The lockfile was in an inconsistent state due to two conflicting dependency upgrades that had landed at different times:

- React had been upgraded from 18 to 19, but peer dependency ranges across several packages still referenced `^18`.
- A root-level `typescript` entry had been bumped to `^5.9.2`, which was not yet available on the registry, causing `ERR_PNPM_NO_MATCHING_VERSION` during `pnpm install --frozen-lockfile`.

**Fix:** Regenerated the lockfile from scratch using a clean Alpine container to avoid any local pnpm store pollution:

```bash
docker run --rm -v "$(pwd):/app" -w /app node:24-alpine \
  sh -c "npm install -g pnpm && pnpm install --no-frozen-lockfile"
```

The `--no-frozen-lockfile` flag is intentional here: it allows pnpm to resolve the new dependency graph and write a fresh, self-consistent lockfile. The result was committed as a single lockfile-only commit.

### 1.8 `builder-store.ts`: `PUT` → `PATCH` for Strategy Updates

**Problem:** The `save()` action in `builder-store.ts` was sending a `PUT /api/v1/strategies/:id` request when updating an existing strategy. The API controller uses `@Patch(':id')` as its NestJS route decorator, which means `PUT` requests to that path returned `404 Not Found`.

**Fix:** Changed the HTTP method from `PUT` to `PATCH` in the strategy update branch of `save()`.

**File:** `apps/user-app/src/stores/builder-store.ts`

```typescript
// Before
const res = await fetch(`/api/v1/strategies/${strategyId}`, {
  method: 'PUT',
  ...
});

// After
const res = await fetch(`/api/v1/strategies/${strategyId}`, {
  method: 'PATCH',
  ...
});
```

## 2. TypeScript Strict-Mode Fixes

These are targeted type-correctness fixes applied across services to satisfy `strict: true`. None of them change runtime behaviour; they exist to make the TypeScript compiler's analysis accurate.

### 2.1 `api-service` — Markets Service Sort Column

**File:** `services/api-service/src/markets/markets.service.ts`

**Problem:** `sort` was typed as `string | undefined`. `Map.get()` requires a `string`, so passing `sort` directly was a type error.

**Fix:**

```typescript
// Before
const col = allowedSortColumns.get(sort);

// After
const col = allowedSortColumns.get(sort ?? 'volume');
```

The fallback value `'volume'` matches the default sort documented in the OpenAPI spec.

### 2.2 `api-service` — Orders Controller Request Type

**File:** `services/api-service/src/orders/orders.controller.ts`

**Problem:** The `cancelOrder` handler received `req` with an implicit `any` type from `@Req()`, causing the expression `req.user.sub` to produce `TS7017: Element implicitly has an 'any' type`.

**Fix:** Added an explicit inline type annotation on the parameter:

```typescript
async cancelOrder(
  @Param('id') id: string,
  @Req() req: { user: { sub: string } },
) { ... }
```

## 3. Database Seeds

### 3.1 `seed-news-whales.sql` — Table Name Casing Fixes

**Problem:** Earlier versions of the seed file used Prisma's default PascalCase model names (`"User"`, `"Market"`, `"Token"`) as SQL table names. PostgreSQL's default behaviour when Prisma creates tables without an explicit `@@map` directive is to use lowercase snake_case names. The SQL queries were failing with `relation "User" does not exist`.

Additionally, a filter predicate used `"closedAt" IS NULL` to find open markets, but the actual boolean column is named `closed` (a `Boolean` field, not a nullable timestamp).

**Fixes applied:**

| Incorrect | Corrected |
|---|---|
| `FROM "User"` | `FROM users` |
| `FROM "Market"` | `FROM markets` |
| `FROM "Token"` | `FROM tokens` |
| `WHERE "closedAt" IS NULL` | `WHERE closed = FALSE` |

### 3.2 `seed-whale-alerts.sql` — Token Table Name Fix

Same `"Token"` → `tokens` casing fix applied to the whale alerts seed, which references token IDs when building alert records.

### 3.3 Post-Seed State

After running both seeds against a fresh data import, the database contained:

| Entity | Count |
|---|---|
| Users set to `approved = TRUE` | 41 |
| News articles inserted | 10 |
| News signals inserted | 22 |
| Whale profiles inserted | 8 |
| Whale alerts inserted | 15 |

### 3.4 How to Run the Seeds

```bash
# News articles, signals, whale profiles, and alerts
docker compose -f docker-compose.infra.yml exec -T postgres \
  psql -U polyforge -d polyforge < prisma/seed-news-whales.sql

# Whale alerts only (targeted re-seed)
docker compose -f docker-compose.infra.yml exec -T postgres \
  psql -U poly -d polyforge < prisma/seed-whale-alerts.sql
```

> **Note:** `seed-news-whales.sql` must be run before `seed-whale-alerts.sql` if starting from an empty database, because the whale alerts seed assumes whale profiles already exist.

## 4. New Features Built

### 4.1 Market Slot System

**File:** `apps/user-app/src/components/builder/block-definitions.ts`

#### Motivation

Previously, all strategy blocks that referenced a market used a free-text `tokenId` field. This meant a strategy built for one specific market could not be reused on another without manually editing every block's configuration. Strategies were not portable.

#### What Changed

A new field type `market_slot` was added to the `BlockField` union type:

```typescript
export interface BlockField {
  key: string;
  label: string;
  type: 'text' | 'number' | 'select' | 'market_slot';
  placeholder: string;
  options?: string[];
}
```

All 17 blocks that previously had a hardcoded `tokenId` text field now use a `market_slot` dropdown field instead. The available values are `$MARKET_A` through `$MARKET_E` — symbolic placeholders that are resolved to real market/token IDs at execution time via the [market binding UI](#execution-panel) in the Execution Panel.

#### Result

Strategies are now portable: the same strategy graph works on any market by changing bindings in the Execution Panel without touching the canvas.

### 4.3 Strategy Wiring Semantics

**Files:**
- `services/strategy-engine/src/strategy/strategy-registry.service.ts` (backend enforcement)
- `apps/user-app/src/components/builder/nodes/block-node.tsx` (frontend visual feedback)
- `apps/user-app/src/pages/strategies/strategy-builder.tsx` (canvas banner)

#### Overview

Strategies are built by connecting blocks on a canvas using React Flow edges. Prior to this feature, all blocks on the canvas were always executed, regardless of whether they were connected to anything. This created silent failures: a user could place an action block on the canvas without wiring it to a trigger, and it would either never fire or fire unconditionally.

The wiring semantics feature introduces explicit rules about what it means for a block to be "active":

| Block Type | Requirement to Execute |
|---|---|
| Safety | Always active (global risk guards) |
| Trigger | Must have at least one outgoing edge |
| Condition | Must have at least one incoming AND one outgoing edge |
| Action | Must have at least one incoming edge |

See the full technical deep-dive at [docs/architecture/wiring-semantics.md](./architecture/wiring-semantics.md).

## 5. Bug Fixes

### 5.1 Session Expiry Silent Fail in Strategy Builder

**File:** `apps/user-app/src/pages/strategies/strategy-builder.tsx`

**Problem:** When a user's session expired mid-edit, the `save()` call in `builder-store.ts` would receive a `401 Unauthorized` response from the API. The store threw a generic error with message `SESSION_EXPIRED`, but the `onSave` handler in `strategy-builder.tsx` had no specific handling for this case. The user saw a brief generic error toast, which disappeared after a few seconds with no indication that their work was still in the store.

**Fix:** The `onSave` handler now checks for `message === 'SESSION_EXPIRED'` and shows a persistent Sonner toast:

```typescript
if (message === 'SESSION_EXPIRED') {
  toast.error('Session expired — your work is preserved', {
    description: 'Log in again to save your strategy.',
    duration: Infinity,
    action: {
      label: 'Log in',
      onClick: () => { window.location.href = '/login'; },
    },
  });
}
```

Key characteristics of this toast:
- `duration: Infinity` — it stays until dismissed or the user navigates away.
- The "Log in" action button navigates to `/login` without a full page reload that would wipe the in-memory Zustand store state.
- The builder store's `dirty` flag and canvas state are preserved across the navigation because the store is initialised at module load time, not at component mount time.

### 5.2 Block Palette Actions Tab Clipped

**File:** `apps/user-app/src/components/builder/block-palette.tsx`

**Problem:** On shorter viewport heights, the tab bar in the block palette (Safety / Triggers / Conditions / Actions) would overflow its container. The rightmost tab(s) would be clipped with no visual indicator that more content existed off-screen.

**Fix:** A `ResizeObserver` was attached to the tab bar container element. When the observed `contentRect.width` is less than the `scrollWidth` of the container, an amber gradient overlay is absolutely positioned at the right edge to serve as a scroll-hint affordance. The overlay appears and disappears reactively as the panel is resized.

### 5.3 React Autofill / Programmatic Input State Desync

**File:** `apps/user-app/src/components/builder/block-palette.tsx`

**Problem:** Browser autofill and password managers populate input fields by dispatching synthetic events that React's synthetic event system does not always capture via `onChange`. Specifically, `onChange` fires for keyboard input but not always for programmatic value injection. This meant that when a user's browser pre-filled the strategy name or description fields, the Zustand store was never updated with the autofilled value. Saving the strategy would overwrite the user-visible content with the store's previous (empty) state.

**Fix:** Added `onBlur` handlers as fallbacks on all text inputs in `block-palette.tsx` (name, description, tags, `tickMs`). The `onBlur` handler reads `e.currentTarget.value` and updates the store unconditionally. Because `onBlur` fires when focus leaves the element — regardless of how the value was set — this catches autofill, paste, and any other programmatic input mechanism.
